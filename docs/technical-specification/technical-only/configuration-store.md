Принято почти всё. Из твоего списка одно место, где я буду возражать — про «сабмодуль», ниже объясню; остальное вносится как есть. Сначала короткая сводка правок, потом документ целиком в v2.

**Что меняется по твоим замечаниям:**

- назначение переформулировано: непубличные артефакты с разграничением по правам, а не «хранилище секретов» в смысле Vault;
- раскладка разделена: **прод (Linux) — симлинки, dev (Windows) — копирование**;
- `config-sync` получает чёткое конфликтное поведение + проверку чистоты рабочей копии;
- идемпотентность — конкретное определение;
- структура: среды на верхнем уровне, конфиги и документы логически разделены;
- SSH-доступ: доступ к приватному репо — отдельная проверка, не «предусловие уже проверяется»;
- защита от повторения — двухуровневая (pre-commit + серверная проверка), одним хуком не обходимся.

**Возражение — сабмодуль.** Если «сабмодулем» ты имел в виду буквально git submodule в публичном репо — не надо, вот почему: (1) URL приватного репо торчит в публичном `.gitmodules` — любой увидит, что он существует, а боты сканят именно это; (2) `git clone --recurse-submodules` у человека без доступа упадёт с ошибкой — а это твой же критерий готовности из setup-задачи; (3) `git submodule update --init --recursive` в setup-скрипте придётся учить пропускать приватный — хрупко. Отдельный репозиторий, клонируемый **рядом** (сиблингом), решает всё: setup при наличии доступа клонирует его сам, при отсутствии — фолбэк на `.env.example`, который у нас и так предусмотрен. Если ты имел в виду просто «репозиторий» — тогда ок, возражение снимается, оставляем имя configuration-store.

# ТЗ: configuration-store — приватное хранилище конфигураций (v2)

## 1. Назначение

Отдельный приватный репозиторий для непубличных артефактов проекта: рабочих конфигураций сервисов (env-файлы с реальными значениями) и внутренних документов. Разграничение доступа — правами на репозиторий (участники, SSH-ключи), компенсация рисков — ротацией при утечке.

**Чем это не является:** хранилищем секретов в смысле Vault. Доступ к машине ≡ доступ к конфигурациям; репозиторий не шифрует, не выдаёт по запросу, не аудитирует обращения. Это осознанно: уровень защиты соответствует текущему масштабу (одна машина, маленькая команда).

## 2. Проблема

Рабочие env-файлы и документы лежат в публичном репозитории: секреты доступны любому (включая историю коммитов), граница «публичное/приватное» не проводится нигде.

## 3. Отклонённая альтернатива

Self-hosted сервис конфигураций (модель Vault/Consul) — отклонён: все сервисы на одной машине, отдельный сервис добавляет точку отказа без выгоды. Условие возврата: несколько машин или больше одной среды развёртывания.

Вторая альтернатива — configuration-store как сабмодуль публичного репо — отклонена: URL приватного репо раскрывается в `.gitmodules`, рекурсивный клон падает у посторонних, смешиваются уровни доступа. Configuration-store клонируется отдельным репозиторием рядом с основным.

## 4. Что строим

### 4.1. Доступ

- **Разработчики** — участники приватного репо, доступ на чтение и запись (коммитят dev-конфиги; смена конфига видна в истории — кто и когда).
- **Прод-машина** — read-only deploy key: прод-машине нечего коммитить, и ключ с правом записи на машине, где лежат прод-секреты, — лишний риск `[№107]`.
- Проверка доступа к configuration-store — отдельный шаг в setup/config-sync (`git ls-remote`), не смешивается с проверкой доступа к публичному репо.

### 4.2. Структура

```
configuration-store/
├── dev/
│   ├── backend/.env.dev
│   └── frontend/.env.dev
│
└── prod/
    ├── backend/.env
    └── frontend/.env
```

- Среда задаётся каталогом (`dev/`, `prod/`), файл хранится без суффикса. Целевое имя при раскладке определяется сервисом (например, backend в dev читает `.env.dev` — раскладка кладёт под этим именем).
- Конфиги и документы разделены на уровне репозиториев: configuration-store — только конфигурации (узкий круг доступа); документы — отдельный приватный репозиторий (широкий круг, отедельная задача)
- Раскладка по средам: **dev-машины получают только `configs/dev/`, прод-машина — только `configs/prod/`**. Прод-конфиги не раскладываются на машинах разработки.

### 4.3. Раскладка

Два режима по среде:

- **dev (Windows-машины) — копирование.** Простое и предсказуемое на любой ОС; риск рассинхрона «работаю со старым env» компенсируется тем, что config-sync вызывается из setup и из make dev.
- **prod (Linux) — симлинки.** Файл всегда актуален без синхронизации; на Linux ограничений нет.

Управляемость файлов (нужно для конфликтного поведения):

- симлинк управляем по определению (ссылка в известный путь);
- копия управляема, если первой строкой содержит маркер `# managed-by: configuration-store`. Маркер виден человеку, проверяется скриптом, попадает в целевой файл безвредно для формата env.

### 4.4. Поведение `config-sync` при конфликте

Целевой файл существует и **не управляем** (нет маркера / не симлинк) → команда завершается ошибкой, файл не трогается; сообщение: путь к файлу, причина, что сделать (перенести содержимое вручную в configuration-store или удалить файл) — после этого повторный запуск преуспеет.

Целевой файл существует и **управляем** → перезапись содержимым из store (это штатное обновление).

### 4.5. Идемпотентность — определение

Повторный запуск `config-sync` при том же состоянии configuration-store не меняет ничего на целевой машине: содержимое управляемых файлов сверяется перед записью и не перезаписывается при совпадении, дубликаты и бэкапы не создаются, ошибки не возникают. Первый запуск и повторный приводят к одному и тому же целевому состоянию.

### 4.6. Чистота рабочей копии

Рабочая копия configuration-store не предназначена для локальных незакоммиченных изменений. Перед синхронизацией скрипт проверяет `git status`: при наличии незакоммиченных изменений — ошибка со списком файлов. Изменение конфигурации вносится коммитом (фиксируется автор и момент), а не правкой рабочей копии на одной из машин.

### 4.7. Интеграция с setup

Существующая задача setup (создание `backend/.env.dev` из `.env.example`) дополняется: при наличии доступа к configuration-store env подтягивается из него (реальная конфигурация); при отсутствии — создаётся из example с предупреждением «это шаблон без секретов, за доступом — к N». `.env.example` остаются в публичных репо.

## 5. Процесс

**Развёртывание dev:** setup проверяет SSH-доступ к configuration-store → клонирует рядом с основным репо → `config-sync --env dev` → сервис стартует.
**Развёртывание prod:** клон по deploy key → `config-sync --env prod` (симлинки) → сервис стартует.
**Обновление конфигурации:** коммит в configuration-store → на целевой машине `config-sync` (dev — копия, prod — актуализируется симлинками автоматически при изменении файла в рабочей копии store).
**Новый секрет:** значение в store → имя и дефолт в `.env.example` → код читает через слой конфигурации.

## 6. Правила и ограничения

1. **Ротация утёкшего — обязательна** до/параллельно с переездом: всё, что лежало в публичном репо (включая историю), меняется.
2. **Защита от повторения — две линии, одной pre-commit недостаточно:**
   - первая линия — pre-commit хук (gitleaks) локально: быстрая обратная связь до пуша; обходится `--no-verify`, поэтому гарантией не является;
   - вторая линия — **серверная проверка в CI на каждый пуш/PR**: gitleaks в обязательном чеке; обход локального хука ничего не даёт, секрет не попадёт в публичный репозиторий;
   - третья, периодическая — скан истории всего репо раз в месяц и после инцидентов (ловит то, что было до внедрения проверок).
3. Чистка истории публичного репо — не выполняется: ротация закрывает риск, чистка гарантий не даёт (клоны, форки). Отдельная задача — если появится внешнее требование.
4. Права на prod-машине: env-файлы и рабочая копия store — `600`/`700`, недоступны остальным пользователям машины.
5. Секреты не логируются, не выводятся при старте (маскируются), не попадают в тела ошибок.
6. CI-секреты — вне этого ТЗ: для Actions хранятся в секретах платформы, дублирование не допускается.

## 7. Критерии готовности

- configuration-store создан по структуре 4.2; в публичном репо env-файлов и документов нет.
- Ротация выполнена: старые пароли/ключи не работают.
- `config-sync --env dev` на Windows-машине: копирует с маркером; повторный запуск — no-op (файлы не тронуты, время изменения не обновлено).
- `config-sync --env prod` на Linux-машине: симлинки; изменение файла в store актуально без повторной синхронизации.
- Целевой файл без маркера → ошибка, файл не изменён, в сообщении есть путь и инструкция.
- Рабочая копия с незакоммиченными правками → ошибка со списком файлов.
- Прод-конфиги не появлялись на dev-машине ни при каком сценарии запуска.
- CI отклоняет пуш с тестовым секретом; локальный `--no-verify` не спасает.
- setup без SSH-доступа к store создаёт env из example с предупреждением.
- Новый сервис стартует без ручного копирования файлов.
