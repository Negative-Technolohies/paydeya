## 15. Регистрация модератора платформы

### 15.1. Назначение

Процесс описывает создание учётной записи модератора платформы через пригласительную ссылку, сформированную администратором. Самостоятельная регистрация модератора невозможна. Регистрация включает заполнение личных данных и подтверждение обоих контактных способов (email и телефон). После подтверждения создаётся аккаунт с ролью «модератор».

### 15.2. Участники, пред- и постусловия

**Участники:**

- администратор платформы (инициатор создания приглашения);
- новый модератор платформы (получатель ссылки, заполняет данные);
- система (сервер) управляет токенами, обрабатывает регистрацию, отправляет коды подтверждения.

**Предусловия:**

- администратор авторизован и имеет право создания приглашений для регистрации;
- существует роль «модератор» в справочнике `roles`;
- у нового модератора есть доступ к email и телефону, которые он укажет при регистрации.

**Постусловия (успешное завершение):**

- создан пользователь с ролью «модератор»;
- оба контакта (email, телефон) подтверждены;
- пользователь может войти в систему (возможно, с обязательной 2FA, если настроена);
- пригласительный токен помечен как использованный.

### 15.3. Входные данные

**При формировании приглашения (администратор):**

| Поле                 | Обязательность | Валидация                                                              |
| -------------------- | -------------- | ---------------------------------------------------------------------- |
| Роль                 | обязательно    | выбор из справочника ролей (в данном случае «модератор»)               |
| Срок действия ссылки | опционально    | если не указан, используется значение по умолчанию (например, 72 часа) |

**При активации ссылки (новый модератор):**

| Поле    | Обязательность | Валидация                                                          |
| ------- | -------------- | ------------------------------------------------------------------ |
| ФИО     | обязательно    | непустое, до 150 символов                                          |
| Email   | обязательно    | корректный формат, нормализуется, уникальность среди пользователей |
| Телефон | обязательно    | корректный формат, нормализуется, уникальность среди пользователей |
| Пароль  | обязательно    | не менее 8 символов, буквы и цифры                                 |

Роль назначается сервером принудительно на основе данных токена; пользователь не может её изменить.

### 15.4. Основной процесс

**Формирование пригласительной ссылки:**

1. Администратор в интерфейсе управления пользователями выбирает «Создать приглашение».
2. Выбирает роль «модератор», при необходимости указывает срок действия.
3. Сервер генерирует токен: случайная строка (UUID или криптостойкая последовательность), в которую вшита информация о роли и сроке действия. Сам токен сохраняется в БД (или Redis) с полями: `token_hash`, `role_id`, `created_by`, `created_at`, `expires_at`, `is_activated`, `activated_at`, `activated_by`.
4. Сервер формирует ссылку вида `https://platform.com/register?token=<token>` и возвращает её администратору.
5. Администратор передаёт ссылку новому модератору через внешний защищённый канал. Пароль для активации ссылки не требуется.

**Активация ссылки и регистрация:**

1. Новый модератор переходит по полученной ссылке.
2. Сервер проверяет токен: существует, не истёк, не активирован ранее, роль разрешена.
3. Если токен валиден, открывается форма регистрации с полями: ФИО, email, телефон, пароль.
4. Модератор заполняет поля и отправляет форму.
5. Сервер валидирует данные (см. 15.3), проверяет уникальность email и телефона (среди всех пользователей, включая неподтверждённых).
6. При ошибках — соответствующая ветка 15.5.
7. Если всё корректно, сервер создаёт запись в `users` со статусом `unconfirmed`, с указанными email и phone, но `email_verified = false`, `phone_verified = false`. Пользователь не может войти до подтверждения обоих контактов.
8. Сервер генерирует два кода подтверждения: для email (ссылка с токеном) и для телефона (SMS-код). Хранит их в Redis (как описано в 15.7), отправляет пользователю.
9. Модератор подтверждает email (переход по ссылке из письма) и телефон (ввод кода в интерфейсе). Подтверждения могут быть в любом порядке.
10. Когда оба контакта подтверждены, сервер устанавливает `email_verified = true`, `phone_verified = true`, меняет статус пользователя на `active`.
11. Токен приглашения помечается `is_activated = true`, `activated_at = now()`, `activated_by = user_id`.
12. Пользователь считается зарегистрированным и может войти (с учётом 2FA, если она обязательна для модераторов).

### 15.5. Ошибочные и альтернативные ветки

1. **Токен недействителен (не существует, истёк, уже использован).**  
   Пользователь видит страницу «Ссылка недействительна или уже использована». Администратор может создать новую.

2. **Email или телефон уже заняты.**  
   Сервер возвращает ошибку «Контакт уже используется». Регистрация не продолжается; пользователь должен обратиться к администратору для решения (или использовать другой контакт).

3. **Пароль не соответствует политике.**  
   Ошибка валидации, форма не отправляется.

4. **Не подтверждён один из контактов.**  
   Пользователь может повторно запросить отправку кода/ссылки (с ограничениями как в разделе 3.6 п.4). Пока оба не подтверждены, аккаунт остаётся `unconfirmed`, вход запрещён (кроме, возможно, страницы ожидания подтверждения).

5. **Истёк срок жизни неподтверждённой записи.**  
   Согласно разделу 3.5.7, запись удаляется через 1 час после последней активности (или после последней повторной отправки подтверждения). Для модератора, если он не завершил регистрацию, его данные удаляются, контакты освобождаются. Пригласительный токен остаётся, но пользователь может начать заново по той же ссылке, если токен не истёк.

6. **Сбой при отправке кода.**  
   Пользователь может запросить повторную отправку, соблюдая лимиты.

### 15.6. Правила и ограничения

1. Пригласительная ссылка создаётся только администратором с правом `create_invitation`.
2. Токен одноразовый, имеет срок действия (по умолчанию 72 часа) и привязку к роли.
3. Роль при регистрации назначается сервером на основе токена, пользователь не может её изменить.
4. Для модератора обязательны оба контакта: email и телефон, и оба должны быть подтверждены.
5. Пароль хранится в виде хеша.
6. Процесс подтверждения контактов использует Redis, как и для других ролей; правила TTL и лимитов совпадают с разделом 3.6 п.4.
7. Вход в систему для модератора возможен только после активации аккаунта (подтверждены оба контакта). Двухфакторная аутентификация при входе будет описана отдельно, но предполагается обязательной.
8. Все действия с приглашениями логируются (создание, активация, попытки использования).

### 15.7. Изменения модели данных

**Таблица `users`:**

- Поля `email` и `phone` сделать nullable. Добавить CHECK-ограничение: `(email IS NOT NULL) OR (phone IS NOT NULL)` — хотя бы одно заполнено. Для модераторов по сценарию оба заполнены, но в целом ограничение остаётся.
- Поле `full_name` остаётся NOT NULL, так как при регистрации модератора требуется ФИО.
- Статусы: `unconfirmed`, `active`, `blocked` (как в 3.7). Для модератора активация происходит после подтверждения обоих контактов.

**Пригласительные токены:**

Создать таблицу `invitation_tokens`:

| Поле         | Тип                                   | Комментарий                                 |
| ------------ | ------------------------------------- | ------------------------------------------- |
| token_hash   | String, PK                            | хеш токена (сам токен не храним)            |
| role_id      | BigInteger, FK → `roles.id`, NOT NULL | роль, назначаемая при регистрации           |
| created_by   | BigInteger, FK → `users.id`, NOT NULL | администратор, создавший приглашение        |
| created_at   | datetime, NOT NULL                    |                                             |
| expires_at   | datetime, NOT NULL                    | срок действия                               |
| is_activated | Boolean, NOT NULL, default false      | был ли использован                          |
| activated_at | datetime, NULL                        | когда активирован                           |
| activated_by | BigInteger, FK → `users.id`, NULL     | кто активировал (user_id нового модератора) |
