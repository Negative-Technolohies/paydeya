## 16. Модерация изменений данных преподавателя

### 16.1. Назначение

Процесс описывает подачу преподавателем заявки на создание или изменение публичных данных профиля, рассмотрение заявки модератором платформы и вынесение вердикта. Только после положительного вердикта изменения применяются к профилю и становятся видимыми публично. При отклонении изменения не применяются, преподаватель получает причину.

Процесс также описывает действия модератора при обнаружении серьёзных нарушений: бан аккаунта напрямую (если есть право) или через запрос администратору.

### 16.2. Участники, пред- и постусловия

**Участники:**

- преподаватель (инициатор заявки);
- модератор платформы с правом `review_tutor_profile_changes` (рассматривает заявку и выносит вердикт);
- модератор платформы с правом `ban_user` (может забанить аккаунт при серьёзном нарушении);
- администратор (рассматривает запросы на бан, если у модератора нет права `ban_user`);
- система (регистрирует заявку, уведомляет, применяет изменения при одобрении, ведёт историю).

**Предусловия:**

- преподаватель авторизован и имеет активную учётную запись (`users.status = 'active'`, `users.is_banned = false`);
- преподаватель заполнил обязательные поля профиля (для первичной заявки) или инициировал изменение одного или нескольких публичных полей;
- существует хотя бы один модератор с правом `review_tutor_profile_changes`;
- система создала заявку со статусом `pending` и уведомила модераторов с нужным правом.

**Постусловия (успешное завершение):**

- заявка переведена в статус `approved` или `rejected`;
- при `approved`: изменённые данные применены к профилю; если заявка была первичной (`creation`), профиль становится публичным и анкета активируется;
- при `rejected`: профиль остаётся без изменений (если первичная заявка — не публикуется), преподаватель получает уведомление с причиной;
- создана запись вердикта с указанием модератора, времени и (при отклонении) комментария;
- при серьёзном нарушении и наличии права `ban_user` у модератора аккаунт преподавателя может быть забанен (`users.is_banned = true`); в противном случае создаётся запрос на бан администратору.

### 16.3. Входные данные

**При создании заявки (преподаватель):**

| Поле            | Обязательность | Валидация                                                                                                                                                               |
| --------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Тип заявки      | обязательно    | `creation` (первичное заполнение) или `update` (изменение существующих данных)                                                                                          |
| Изменяемые поля | обязательно    | набор полей с новыми значениями. Допустимые публичные поля: ФИО, аватар, «о себе», опыт, город, цена, формат, предметы (состав будет уточнён в сценарии преподавателя). |

**При вынесении вердикта (модератор):**

| Поле        | Обязательность                                    | Валидация              |
| ----------- | ------------------------------------------------- | ---------------------- |
| Решение     | обязательно                                       | `approve` или `reject` |
| Комментарий | обязателен при `reject`, опционален при `approve` | до 1000 символов       |

### 16.4. Основной процесс

**Создание заявки преподавателем:**

1. Преподаватель в личном кабинете открывает форму редактирования профиля или заполняет его впервые.
2. Вносит изменения в публичные поля.
3. Нажимает «Отправить на модерацию».
4. Сервер сохраняет заявку в таблице `profile_change_requests` со статусом `pending`. Текущие данные профиля не изменяются.
5. Если это первичная заявка (`creation`), профиль преподавателя остаётся непубличным (`users.is_public = false`, `tutor_profiles.is_active = false`); если обновление (`update`), текущие данные остаются публичными (если они были одобрены ранее).
6. Сервер отправляет уведомление модераторам, имеющим право `review_tutor_profile_changes`.
7. Преподаватель видит статус заявки «на рассмотрении».

**Рассмотрение заявки модератором:**

1. Модератор (с правом `review_tutor_profile_changes`) открывает список заявок или получает уведомление.
2. Открывает заявку и видит текущие данные профиля и предлагаемые изменения (для `update`) или только предлагаемые данные (для `creation`).
3. Проверяет данные на соответствие правилам платформы (отсутствие нецензурной лексики, рекламы, некорректных значений и т.п.).
4. Если всё корректно — выбирает «Одобрить» (`approve`), комментарий необязателен.
5. Если есть нарушения — выбирает «Отклонить» (`reject`) и указывает причину в комментарии.
6. Сервер создаёт запись вердикта в таблице `moderation_decisions` с указанием заявки, модератора, решения, комментария и времени.
7. Если вердикт `approve`:
   - Сервер применяет изменения: копирует новые значения из заявки в `tutor_profiles`;
   - Если тип заявки `creation`, устанавливает `users.is_public = true`, `tutor_profiles.is_active = true`;
   - Если тип `update`, публичные флаги не меняются (если они уже были true);
   - Заявка получает статус `approved`.
8. Если вердикт `reject`:
   - Изменения не применяются;
   - Если первичная заявка, `users.is_public` остаётся false, `tutor_profiles.is_active` остаётся false;
   - Преподавателю отправляются уведомления (внутреннее сообщение, email, SMS) с текстом причины;
   - Заявка получает статус `rejected`.

**Обработка серьёзных нарушений (бан):**

9. Если модератор при рассмотрении заявки обнаруживает серьёзное нарушение (нецензурное ФИО, реклама, мошенничество и т.п.) и у него есть право `ban_user`:
   - Модератор выбирает действие «Забанить аккаунт».
   - Сервер выполняет бан: устанавливает `users.is_banned = true`, `users.is_public = false`, `tutor_profiles.is_active = false`.
   - Создаётся вердикт с решением `reject` (или отдельная запись о бане), возможно с комментарием.
   - Преподаватель получает уведомление о блокировке по всем каналам.
   - Заявка получает статус `rejected` (или `banned` — по решению; для простоты оставляем `rejected`).

10. Если у модератора нет права `ban_user`, но он считает, что нужен бан:
    - Создаёт запрос на бан администратору (таблица `ban_requests`).
    - До решения администратора профиль может быть скрыт (`users.is_public = false`, `tutor_profiles.is_active = false`).
    - Администратор рассматривает запрос и либо банит аккаунт (устанавливает `users.is_banned = true`), либо отклоняет запрос (тогда профиль остаётся скрытым, но не забаненным; модератор может повторить запрос).

**Примечание:** администратор также имеет право `ban_user` по умолчанию.

### 16.5. Ошибочные и альтернативные ветки

1. **Нет модераторов с правом `review_tutor_profile_changes`.**  
   Заявка остаётся в очереди. Администратор должен назначить права.

2. **Модератор без права `review_tutor_profile_changes` пытается обработать заявку.**  
   Сервер возвращает 403; заявка не изменяется.

3. **Заявка уже обработана (повторное действие модератора).**  
   Сервер блокирует изменение вердикта, сообщая «Заявка уже обработана».

4. **Преподаватель подал новую заявку, пока предыдущая ещё на рассмотрении.**  
   По правилу одна активная заявка на профиль. Сервер блокирует создание новой, предлагает дождаться решения.

5. **Сбой при отправке уведомлений.**  
   Заявка сохраняется; пользователь может увидеть статус в кабинете. Уведомления можно повторить.

6. **В заявке изменены только непубличные поля (пароль, email, телефон и т.п.).**  
   Такие изменения не требуют модерации и обрабатываются отдельными процессами; заявка не создаётся.

7. **Модератор выбрал «Забанить», но у него нет права `ban_user`.**  
   Система не выполняет бан, а предлагает создать запрос администратору (как в шаге 10).

8. **Администратор отклонил запрос на бан.**  
   Профиль остаётся скрытым (`users.is_public = false`, `tutor_profiles.is_active = false`), но не забаненным. Модератор может повторно отправить запрос.

### 16.6. Правила и ограничения

1. Все изменения публичных данных преподавателя проходят через заявки. Непосредственное редактирование профиля без заявки невозможно.
2. Для каждого преподавателя может существовать не более одной активной заявки на изменение профиля (статус `pending`).
3. Право рассматривать заявки на изменение профилей преподавателей — `review_tutor_profile_changes`. Оно назначается администратором. Модераторы без этого права не видят и не могут обрабатывать такие заявки.
4. Право банить аккаунты — `ban_user`. Если модератор имеет это право, он может забанить напрямую при серьёзном нарушении. Иначе — создаёт запрос администратору.
5. Вердикт по заявке выносится один раз, изменить его нельзя. Можно только подать новую заявку.
6. При одобрении заявки типа `update` изменения применяются немедленно, профиль остаётся публичным (`users.is_public = true`).
7. При отклонении первичной заявки (`creation`) профиль не становится публичным, преподаватель может подать новую заявку.
8. При отклонении заявки на обновление текущие публичные данные остаются без изменений; профиль продолжает быть публичным с прежними данными.
9. Уведомления преподавателю об отклонении отправляются по трём каналам: внутреннее сообщение, email, SMS. Текст содержит причину из комментария модератора.
10. История заявок и вердиктов сохраняется для аудита.
11. Скрытие профиля (`users.is_public = false`, `tutor_profiles.is_active = false`) не равно бану. Бан — это `users.is_banned = true`, который также автоматически скрывает профиль.
12. Все действия модератора логируются (время, модератор, действие, комментарий).

### 16.7. Изменения модели данных

**Таблица `users` — добавить поля:**

| Поле        | Тип                              | Комментарий                                                                                                                 |
| ----------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `is_banned` | Boolean, NOT NULL, default false | признак бана аккаунта                                                                                                       |
| `is_public` | Boolean, NOT NULL, default true  | общая видимость аккаунта; для преподавателя false до первичного одобрения, true после; для модераторов/администраторов true |

**Таблица `tutor_profiles` — изменения:**

- Убрать поле `is_public` (если было).
- Добавить поле `is_active` (Boolean, NOT NULL, default false) — активна ли анкета преподавателя (публична и участвует в поиске, откликах, каталоге).

**Добавить таблицу `profile_change_requests`:**

| Поле             | Тип                                            | Комментарий                       |
| ---------------- | ---------------------------------------------- | --------------------------------- |
| id               | BigInteger, PK                                 |                                   |
| tutor_id         | BigInteger, FK → `tutor_profiles.id`, NOT NULL | чей профиль                       |
| type             | String, NOT NULL                               | `creation` или `update`           |
| status           | String, NOT NULL, default 'pending'            | `pending`, `approved`, `rejected` |
| proposed_changes | JSONB                                          | новые значения публичных полей    |
| created_at       | datetime, NOT NULL                             | время подачи заявки               |
| processed_at     | datetime, NULL                                 | когда обработана                  |

**Добавить таблицу `moderation_decisions`:**

| Поле         | Тип                                                     | Комментарий            |
| ------------ | ------------------------------------------------------- | ---------------------- |
| id           | BigInteger, PK                                          |                        |
| request_id   | BigInteger, FK → `profile_change_requests.id`, NOT NULL |                        |
| moderator_id | BigInteger, FK → `users.id`, NOT NULL                   |                        |
| decision     | String, NOT NULL                                        | `approve` или `reject` |
| comment      | String(1000), NULL                                      | причина при отклонении |
| created_at   | datetime, NOT NULL                                      |                        |

**Добавить таблицу `ban_requests`:**

| Поле             | Тип                                            | Комментарий                       |
| ---------------- | ---------------------------------------------- | --------------------------------- |
| id               | BigInteger, PK                                 |                                   |
| requested_by     | BigInteger, FK → `users.id`, NOT NULL          | модератор                         |
| tutor_profile_id | BigInteger, FK → `tutor_profiles.id`, NOT NULL |                                   |
| reason           | String(1000), NOT NULL                         | причина                           |
| status           | String, NOT NULL, default 'pending'            | `pending`, `approved`, `rejected` |
| created_at       | datetime, NOT NULL                             |                                   |
| resolved_at      | datetime, NULL                                 |                                   |
| resolved_by      | BigInteger, FK → `users.id`, NULL              | администратор                     |

**Индексы и ограничения:**

- Частичный уникальный индекс на `(tutor_id) WHERE status = 'pending'` в `profile_change_requests`.
- Уникальный индекс на `(request_id)` в `moderation_decisions` — один вердикт на заявку.

**Правки согласованных правил:**

1. Разделы 7, 8, 9 должны быть синхронизированы: «опубликованный профиль» теперь означает `users.is_public = true` и `tutor_profiles.is_active = true`. Необходимо внести соответствующие правки в эти разделы (в их формулировках про критерии показа репетиторов).
2. Раздел 14 (отзывы) не зависит от публичности профиля; для оставления отзыва нужна подтверждённая договорённость. Дополнительных правок не требуется.
