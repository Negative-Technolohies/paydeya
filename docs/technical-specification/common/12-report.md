## 12. Жалоба на пользователя (общий случай)

### 12.1. Назначение

Процесс позволяет авторизованному пользователю (ученику, репетитору) сообщить модерации о нарушении правил другим пользователем. Жалоба может быть подана вне зависимости от контекста: при просмотре профиля, анкеты, отзыва, контента или в другом месте, где замечено нарушение.

Граница раздела: здесь описывается только общий механизм подачи жалобы. Случай, когда жалоба подаётся из диалога (переписки), будет описан отдельным сценарием (позже), так как там добавляется привязка к диалогу и дополнительные проверки.

### 12.2. Участники, пред- и постусловия

**Участники:**

- авторизованный пользователь (инициатор жалобы);
- пользователь, на которого подаётся жалоба (ответчик);
- система (сервер) принимает и сохраняет жалобу;
- модератор (получает жалобу для рассмотрения).

**Предусловия:**

- инициатор авторизован и активен;
- ответчик существует и не является самим инициатором;
- инициатор ещё не подавал активную (не рассмотренную) жалобу на этого же пользователя (защита от дублирования на уровне пары пользователей, без привязки к контексту).

**Постусловия (успешное завершение):**

- создана запись о жалобе (complaint) со статусом «новая»;
- инициатор видит подтверждение «Жалоба принята»;
- жалоба появляется в очереди модератора;
- модератор может просмотреть детали жалобы и, при необходимости, связанный контекст (если он был указан).

### 12.3. Входные данные

| Поле            | Обязательность                             | Валидация                                                                                                                          |
| --------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `respondent_id` | обязательно                                | идентификатор пользователя, на которого подаётся жалоба                                                                            |
| `reason`        | обязательно                                | выбор из справочника причин (см. 12.6 п.1)                                                                                         |
| `description`   | нет (обязательно, если `reason = 'other'`) | свободный текст, до 1000 символов, без разметки                                                                                    |
| `context_type`  | нет                                        | строка, описывающая тип контекста (например, `profile`, `questionnaire`, `review`, `video`, `material`). В v1 может отсутствовать. |
| `context_id`    | нет                                        | идентификатор объекта контекста. Используется, если `context_type` указан.                                                         |

Примечание: поля `context_type` и `context_id` вводятся как опциональные на будущее, чтобы при необходимости модератор мог перейти к спорному объекту. В общем сценарии они необязательны; конкретное поведение будет уточнено при описании сценариев модератора.

### 12.4. Основной процесс

1. Пользователь замечает нарушение со стороны другого пользователя (например, в профиле, анкете, отзыве, комментарии, видео и т.п.).
2. Пользователь нажимает «Пожаловаться» (кнопка доступна в различных местах: профиль пользователя, карточка анкеты, отзыв, контент и т.д.).
3. Система открывает форму жалобы с полями: причина (выпадающий список) и дополнительное описание (текстовое поле).
4. Пользователь выбирает причину, при необходимости вводит описание.
5. Пользователь отправляет жалобу.
6. Сервер проверяет:
   - пользователь авторизован;
   - ответчик существует и не является инициатором;
   - нет уже существующей активной жалобы от этого инициатора на этого же ответчика (без учёта контекста);
   - не превышен суточный лимит жалоб (см. 12.6 п.2).
7. При успехе сервер создаёт запись в таблице `complaints` с полями: complainant_id, respondent_id, reason, description, context_type (если указан), context_id (если указан), status = 'new', created_at.
8. Сервер отправляет уведомление модератору (или жалоба появляется в очереди модератора; детали в сценарии модератора).
9. Пользователь видит сообщение «Жалоба принята. Модератор рассмотрит её в ближайшее время».
10. Дальнейшие действия модератора описаны в отдельном сценарии.

### 12.5. Ошибочные и альтернативные ветки

1. **Попытка пожаловаться на себя** — сервер отклоняет с сообщением «Нельзя пожаловаться на себя».
2. **Уже существует активная жалоба на этого пользователя** — сервер не создаёт дубликат; возвращает сообщение «Вы уже пожаловались на этого пользователя».
3. **Превышен суточный лимит жалоб** — сервер отклоняет создание, пользователь видит сообщение «Вы превысили лимит жалоб на сегодня. Попробуйте позже».
4. **Пустая причина или не заполнено описание при причине «другое»** — форма не отправляется, показываются ошибки валидации.
5. **Сбой при отправке уведомления модератору** — жалоба сохранена; модератор увидит её в очереди при следующем обновлении.
6. **Указан несуществующий context_id** — сервер может проигнорировать контекст или отклонить запрос; рекомендуется игнорировать некорректный контекст, сохраняя жалобу без него.

### 12.6. Правила и ограничения

1. Справочник причин жалоб (enum): `spam`, `insult`, `fraud`, `other`. Названия и состав могут быть расширены; на данном этапе фиксируем эти четыре.
2. Лимит подачи жалоб: не более 5 жалоб в сутки на одного пользователя (предлагаемое значение). Точное число может быть изменено настройкой.
3. Защита от дублирования: один пользователь может иметь не более одной активной (не рассмотренной) жалобы на другого пользователя, независимо от контекста.
4. Жалоба не привязана к конкретному объекту, если только пользователь не указал контекст. В v1 контекст не обязателен.
5. Пользователь не видит статус рассмотрения жалобы после отправки (на этапе v1). Подтверждение только «жалоба принята».
6. Жалоба не блокирует автоматически взаимодействие между пользователями; ограничения накладываются только после решения модератора.
7. Факт подачи жалобы конфиденциален: ответчик не уведомляется о жалобе до принятия модератором решения (если вообще уведомляется).

### 12.7. Изменения модели данных

Необходимо создать новую таблицу `complaints`:

| Поле              | Тип                                    | Комментарий                                                                         |
| ----------------- | -------------------------------------- | ----------------------------------------------------------------------------------- |
| id                | BigInteger, PK                         |                                                                                     |
| complainant_id    | BigInteger, FK → `users.id`, NOT NULL  | кто подал жалобу                                                                    |
| respondent_id     | BigInteger, FK → `users.id`, NOT NULL  | на кого подана жалоба                                                               |
| reason            | String (Enum), NOT NULL                | `spam`, `insult`, `fraud`, `other`                                                  |
| description       | String(1000), NULL                     | описание при `other` или дополнительный комментарий                                 |
| context_type      | String, NULL                           | тип контекста (например, `profile`, `questionnaire`, `review`, `video`, `material`) |
| context_id        | BigInteger, NULL                       | идентификатор объекта контекста                                                     |
| status            | String (Enum), NOT NULL, default 'new' | `new`, `under_review`, `resolved`, `dismissed`                                      |
| created_at        | datetime, NOT NULL                     | время подачи                                                                        |
| resolved_at       | datetime, NULL                         | время решения модератором                                                           |
| resolved_by       | BigInteger, FK → `users.id`, NULL      | модератор, принявший решение                                                        |
| decision          | String, NULL                           | `confirmed`, `not_confirmed`                                                        |
| moderator_comment | String(1000), NULL                     | комментарий модератора                                                              |

Индексы: по `(complainant_id, respondent_id)` для быстрой проверки дубликатов; по `status` для очереди модератора.

Примечание: если в будущем появится сценарий «жалоба в диалоге», будет добавлено поле `conversation_id` (nullable) или контекст типа `conversation` в общие поля. Это решение отложено до соответствующего сценария.
