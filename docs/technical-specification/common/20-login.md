## 20. Вход в аккаунт

### 20.1. Назначение

Процесс авторизует существующего пользователя по контакту и паролю, создаёт серверную сессию и приводит в личный кабинет его роли.

Смежное: восстановление пароля и смена контактов — отдельные сценарии (не описаны, вне рамок v1). Регистрация — раздел 3.

### 20.2. Участники, пред- и постусловия

**Участник:** любой пользователь платформы (ученик, репетитор, модератор, администратор) с существующей учётной записью.

**Предусловия:** существует учётная запись с контактом, по которому выполняется вход, и пароль совпадает.

**Постусловия (успех):**

- создана серверная сессия (httpOnly cookie);
- пользователь находится в личном кабинете своей роли;
- при входе с «нового устройства» отправляется уведомление на подтверждённый контакт `[Предложение — см. №100]`.

**Постусловия (блокировка):** при `status=blocked` — сессия не создаётся, сервер перестаёт отвечать на запросы этого пользователя (см. 2.6 п.4).

### 20.3. Входные данные

| Поле                        | Обязательность | Валидация                                                                                                                                                                |
| --------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Контакт (email или телефон) | да             | нормализация та же, что при регистрации (trim/нижний регистр для email, единый формат телефона) — иначе `Test@Mail.com` не найдёт аккаунт, созданный как `test@mail.com` |
| Пароль                      | да             | проверка по хешу; при неверном пароле формат ошибки — 2.5.2                                                                                                              |

Идентификатор для поиска записи: email или телефон в любом сочетании — сервер определяет по формату входной строки. Роль не вводится: определяется записью.

### 20.4. Основной процесс

1. Пользователь открывает форму входа.
2. Вводит контакт и пароль, отправляет.
3. Сервер нормализует контакт и ищет учётную запись.
4. Проверки в порядке: статус учётной записи → пароль (порядок важен — 2.6 п.2).
5. При успехе: создаётся серверная сессия (httpOnly cookie, время жизни и продление — 2.6 п.3), пользователь попадает в личный кабинет своей роли.
6. Учётная запись с неподтверждённым контактом, по которому логинятся, не может существовать в активном статусе по построению (3.4, шаг 12: вход разрешён только по подтверждённым контактам; неподтверждённый контакт отбрасывается при активации) — ветка 2.5.3 покрывает остаточные случаи.
7. При входе, отличающемся от обычного паттерна (новое устройство/браузер), на подтверждённый контакт уходит уведомление «выполнен вход с нового устройства» `[№100]`.

### 20.4а. Проверка статуса перед паролем — зачем

Пользователь с `blocked` не должен даже получать оценку своего пароля: ответ «неверный логин или пароль» заблокированному раскрывает меньше, но правильнее семантически — для заблокированного «вход» не существует как процесс. Приоритет проверок: unconfirmed → 2.5.3; blocked → 2.5.4; затем пароль.

### 20.5. Ошибочные и альтернативные ветки

1. **Аккаунт не найден / неверный пароль.** Одинаковый ответ: 401 `AUTH_INVALID_CREDENTIALS` с общей формулировкой «неверный логин или пароль». Не раскрывать, что именно неверно — иначе перебор контактов возможен даже без знания пароля.
2. **Неверный пароль.** Счётчик неудачных попыток `[№101]`: при 5 подряд → защита (2.5.5).
3. **Аккаунт неподтверждён** (unconfirmed). Вход отклоняется, 403 `ACCOUNT_UNCONFIRMED`, предлагается повторная отправка подтверждения (3.5.6). Кейс: регистрация брошена — запись ещё жива (TTL 1 час).
4. **Аккаунт заблокирован** (blocked). Вход отклоняется, 403 `AUTH_FORBIDDEN_BLOCKED`... — стоп, см. 2.6 п.4: формулировка особая.
5. **Превышен лимит неудачных попыток.** 429 `AUTH_ATTEMPTS_EXCEEDED` `[№101 — параметры]`: окно, счётчик, блокировка или замедление. Предложение: 5 неудач подряд → отказ на 15 минут **без раскрытия, существует ли аккаунт**.
6. **Пароль введён для чужого контакта** (пользователь путает email). Тривиально покрыт веткой 1: «неверный логин или пароль», отличий нет.

### 20.6. Правила и ограничения

1. Вход — по контакту + паролю. OTP/вход по ссылке, соц-логины — вне v1.
2. Порядок проверок: статус учётки → пароль. «Нет аккаунта» и «неверный пароль» неотличимы снаружи (единый ответ, единая задержка — 2.7).
3. Сессия: серверная, httpOnly cookie + CSRF-защита. Время жизни `[№102 — предложение 14 дней неактивности, продление при активности]`. Отзыв: логаут, бан (мгновенно, по статусу — проверка на каждый запрос), смена пароля.
4. **Заблокированный пользователь.** При `blocked` на момент входа: сессия не создаётся, ответ — «аккаунт заблокирован» с формулировкой из сценариев модерации (смежный раздел по банам — формулировки там; если у владельца нет готовой — №103). После бана активная сессия отзывается при первом же запросе (middleware проверяет статус). Детали причины бана в ответе не раскрываются — их знает владелец продуктовых правил банов.
5. Уведомление о входе с нового устройства: письмо/СМС на любой подтверждённый контакт, без действий в уведомлении (не ссылка отмены — обычное информирование) `[№100]`.
6. Лимит попыток входа: параметры — №101. Счётчик на пару (контакт+IP) — см. 2.7.
7. Регистронезависимость и нормализация контактов при поиске записи — как при регистрации.

### 20.7. Изменения модели данных

- Сессии: серверные, хранилище — Redis (структура: `user_id`, `role`, `created_at`, `last_seen`, device-мета `[№100]`) — таблица не заводится, TTL-семантика естественная.
- Счётчик неудачных попыток — Redis, ключ на нормализованный контакт, TTL окна. Не в БД — счётчик оконный и ephemeral, персистить нечего.
- Коды ошибок: `AUTH_INVALID_CREDENTIALS` (401), `AUTH_ATTEMPTS_EXCEEDED` (429), `AUTH_FORBIDDEN_BLOCKED` (403), `ACCOUNT_UNCONFIRMED` (403) — дополняют enum из задачи про конверт.
- Таблица «устройства» не заводится: распознавание «нового устройства» в v1 — эвристика по User-Agent + сессии в Redis, отдельная сущность не нужна `[№100]`.
