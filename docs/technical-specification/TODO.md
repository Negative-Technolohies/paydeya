## 8. Redis (не PostgreSQL)

### `contact_confirmations`

Хранение подтверждений email/телефона при регистрации.

- **Хранилище:** Redis (не таблица PostgreSQL).
- **Назначение:** токены/коды подтверждения, попытки, TTL.
- **Спецификация:** формат ключей, структура значений, политика TTL — **описать отдельно при реализации**.

Ключевые требования (из раздела 3):

- Одно активное подтверждение на пару (user, contact_type).
- Хранится хеш кода/токена, а не значение.
- TTL: email-ссылка — 1 час, SMS-код — 10 минут.
- Лимит попыток ввода: не более 5 на одно подтверждение.
- Лимит повторной отправки: не чаще раза в 60 сек, не более 5 в час и 10 в сутки на учётную запись.
- Выпуск нового подтверждения аннулирует предыдущее того же типа.

## 10. Правки после ревью текущей версии схемы

Раздел фиксирует решения и направления правок после проверки реализованной схемы, описанной в `backend/data_schemas.md`.

### 10.1. `users.status` и блокировки пользователя

Текущая схема содержит одновременно:

- `users.status` со значениями `unconfirmed`, `active`, `blocked`;
- `users.is_banned`.

Такой вариант признан неудачным: `status = blocked` и `is_banned = true` дублируют друг друга, а одно enum-поле `status` плохо подходит для пользовательской модели, потому что состояния могут расширяться и накладываться друг на друга.

Решение:

- убрать поле `users.status`;
- убрать поле `users.is_banned`;
- не хранить `active` / `unconfirmed` / `blocked` как единый статус учётной записи;
- блокировки и ограничения пользователя хранить отдельной сущностью, чтобы сохранять причину, автора решения, сроки, историю и факт снятия ограничения;
- `permissions` использовать для проверки прав на действия, но не подменять ими историю банов и санкций.

Предлагаемая новая таблица:

### `user_restrictions`

Ограничения и санкции пользователя.

| Поле       | Тип                                                                             | Комментарий               |
| ---------- | ------------------------------------------------------------------------------- | ------------------------- |
| id         | UUID, PK                                                                        |                           |
| user_id    | UUID, FK → `users.id`, NOT NULL                                                 | Ограниченный пользователь |
| type       | Enum / String: `ban`, `messaging_block`, `content_block`, `profile_hidden`, ... | Тип ограничения           |
| reason     | String / Text, NULL                                                             | Причина ограничения       |
| created_by | UUID, FK → `users.id`, NOT NULL                                                 | Кто наложил ограничение   |
| starts_at  | datetime, NOT NULL                                                              | Начало действия           |
| ends_at    | datetime, NULL                                                                  | NULL = бессрочно          |
| revoked_at | datetime, NULL                                                                  | Когда ограничение снято   |
| revoked_by | UUID, FK → `users.id`, NULL                                                     | Кто снял ограничение      |
| comment    | String(1000), NULL                                                              | Служебный комментарий     |
| created_at | datetime, NOT NULL                                                              | Время создания записи     |

Правило активности ограничения: ограничение активно, если `starts_at <= now`, `revoked_at IS NULL` и (`ends_at IS NULL` или `ends_at > now`).

Полный бан пользователя выражается активным ограничением `type = 'ban'`. Сервер должен учитывать такие ограничения при входе и при каждом защищённом действии пользователя.

`users.is_banned` не используется даже как денормализованный флаг, чтобы не создавать риск рассинхронизации. Если в будущем появится доказанная проблема производительности на массовых выборках, оптимизацию нужно проектировать отдельно.

### 10.2. Подтверждение email и телефона

Текущая схема содержит boolean-поля:

- `users.email_verified`;
- `users.phone_verified`.

Такой вариант признан недостаточным: он не хранит, какой именно контакт был подтверждён, когда это произошло, менялся ли контакт, какой контакт основной, и не даёт нормальной истории подтверждений.

Решение:

- убрать `users.email_verified` и `users.phone_verified`;
- вынести контакты пользователя и факт их подтверждения в отдельную таблицу;
- Redis использовать только для временного процесса подтверждения (коды, токены, попытки, TTL), а подтверждённый результат хранить в PostgreSQL.

Предлагаемая новая таблица:

### `user_contacts`

Контактные способы пользователя и их состояние подтверждения.

| Поле             | Тип                              | Комментарий                                        |
| ---------------- | -------------------------------- | -------------------------------------------------- |
| id               | UUID, PK                         |                                                    |
| user_id          | UUID, FK → `users.id`, NOT NULL  | Владелец контакта                                  |
| type             | Enum / String: `email`, `phone`  | Тип контакта                                       |
| value            | String, NOT NULL                 | Исходное значение для отображения/связи            |
| normalized_value | String, NOT NULL                 | Нормализованное значение для поиска и уникальности |
| verified_at      | datetime, NULL                   | NULL = контакт не подтверждён                      |
| is_primary       | Boolean, NOT NULL, default false | Основной контакт данного типа или пользователя     |
| created_at       | datetime, NOT NULL               | Время добавления                                   |
| deleted_at       | datetime, NULL                   | Мягкое удаление / замена контакта                  |

Ограничения:

- `normalized_value` должен быть уникален среди активных контактов соответствующего типа;
- у пользователя должен быть минимум один активный контакт;
- для входа можно использовать только подтверждённый контакт;
- смена контакта создаёт/обновляет запись контакта и требует нового подтверждения.

### 10.3. Роль `permissions` в банах и ограничениях

`permissions` остаются механизмом ответа на вопрос «какое действие пользователю разрешено выполнять». Баны и санкции отвечают на другой вопрос: «какое ограничение наложено на пользователя, кем, когда и почему».

Решение:

- не хранить бан как обычный permission;
- использовать `permissions` / `role_permissions` / `user_permission_overrides` для общей модели прав;
- активные `user_restrictions` учитывать поверх permissions при проверке доступа;
- для частичных ограничений можно использовать типы ограничений (`messaging_block`, `content_block`, `profile_hidden`) либо deny-переопределения прав, но история и причина ограничения должны храниться в `user_restrictions`.

### 10.4. Уникальность `roles.name` и `permissions.name`

В текущем описании схемы `backend/data_schemas.md` у таблиц `roles` и `permissions` поле `name` указано как `String, NOT NULL`, но не зафиксирована уникальность.

Решение:

- для `roles.name` добавить ограничение уникальности;
- для `permissions.name` добавить ограничение уникальности.

Обоснование: `name` является системным идентификатором роли/права (`student`, `tutor`, `moderator`, `admin`, `verify_tutor_documents`, `import_external_reviews` и т.п.). Дубли таких значений ломают назначение ролей, сиды и проверки доступа.

### 10.5. Удаление таблицы `refresh_tokens`

В текущей схеме появилась таблица `refresh_tokens`, но в сценариях она не требуется.

Сценарий входа (раздел 20) фиксирует другой подход:

- пользовательская сессия хранится в Redis;
- клиент получает серверную сессию через httpOnly cookie;
- TTL и продление сессии управляются Redis;
- счётчики неудачных попыток входа также хранятся в Redis.

Решение:

- удалить таблицу `refresh_tokens`;
- убрать модель `RefreshToken`;
- убрать связи `User.refresh_tokens`;
- не хранить refresh-токены в PostgreSQL;
- для входа и авторизации ориентироваться на Redis-сессии из сценария 20.

Обоснование: хранение refresh-токенов в PostgreSQL противоречит принятой модели серверных сессий. Для v1 источником состояния сессии должен быть Redis, а не отдельная таблица токенов.

### 10.6. Справочники `education_levels` и `cities`

В текущей схеме справочник `education_levels` не только создаётся, но и заполняется конкретными значениями в миграции:

- `Начальная школа`;
- `Средняя школа`;
- `Старшая школа`;
- `Студент/высшее образование`.

Так делать не нужно в рамках правки схемы. Наполнение справочников должно быть вынесено в отдельную задачу.

Решение по `education_levels`:

- оставить таблицу `education_levels`;
- оставить уникальность `education_levels.name`;
- убрать заполнение конкретными значениями из миграции изменения схемы;
- подготовку состава уровней образования вынести в отдельную задачу на справочники/сиды.

Решение по `cities`:

- оставить таблицу `cities`;
- добавить уникальность для `cities.name`;
- не добавлять конкретные города в миграции изменения схемы;
- наполнение справочника городов вынести в отдельную задачу.

Комментарий: для текущей модели `cities` содержит только `name` и `timezone`, поэтому `cities.name` должен быть уникальным, чтобы не появлялись дубли одного и того же города. Если позже появятся страна/регион или поддержка одноимённых городов, уникальность нужно будет пересмотреть в сторону составного ограничения.

### 10.7. Правки `tutor_profiles`

В текущей схеме `tutor_profiles` содержит спорные поля:

- `city` как обычную строку;
- `verified`;
- `avg_rating`;
- `reviews_count`;
- `verification_status`.

Решение по городу:

- заменить `tutor_profiles.city` на `tutor_profiles.city_id`;
- `city_id` должен быть FK → `cities.id`;
- свободную строку города не хранить, чтобы профиль репетитора использовал общий справочник городов.

Решение по верификации:

- убрать `tutor_profiles.verified`;
- убрать `tutor_profiles.verification_status`;
- источником истины по верификации преподавателя считать таблицу `tutor_verifications`;
- для отображения отметок в профиле и фильтрации в каталоге использовать активные записи `tutor_verifications`.

Обоснование: boolean `verified` и строковый `verification_status` дублируют отдельную модель верификации и не дают понять, что именно подтверждено: личность, диплом, сертификат и т.п. Верификация уже нормально раскладывается через `verification_documents` и `tutor_verifications`, поэтому профиль репетитора не должен хранить второе состояние верификации.

Решение по отзывам и рейтингу:

- оставить `tutor_profiles.avg_rating` как денормализованный агрегат для частого отображения в каталоге, карточках и профиле преподавателя;
- убрать `tutor_profiles.reviews_count`;
- пересчитывать количество опубликованных отзывов по таблицам отзывов при чтении профиля/каталога;
- пересчитывать `avg_rating` транзакционно при создании, редактировании, удалении и импорте отзывов.

Обоснование: средний рейтинг отображается во многих местах и будет часто читаться, поэтому хранить `avg_rating` в профиле оправданно. Отзывы появляются и меняются сравнительно редко, поэтому транзакционный пересчёт рейтинга при изменениях допустим. Количество отзывов хранить отдельным полем не нужно: оно требуется в основном там, где всё равно загружается список отзывов, и может быть посчитано из источника истины.

### 10.8. Предметы и связь анкеты с предметом

В текущей схеме у таблицы `subjects` поле `name` не зафиксировано как уникальное.

Решение по `subjects`:

- добавить уникальность для `subjects.name`.

Обоснование: название предмета является справочным значением. Дубли предметов приведут к некорректной фильтрации, матчингам и связям с анкетами/репетиторами.

В текущей схеме одновременно существуют:

- поле `questionnaires.subject_id`;
- M2M-таблица `questionnaire_subjects`.

Такой вариант противоречит сценарию создания анкеты: анкета создаётся только для одного предмета и не может быть связана с несколькими предметами одновременно.

Решение по анкетам:

- оставить `questionnaires.subject_id` как единственную связь анкеты с предметом;
- `questionnaires.subject_id` должен быть FK → `subjects.id`, NOT NULL;
- удалить таблицу `questionnaire_subjects`;
- удалить модель `QuestionnaireSubject` и связанные импорты/relationship.

Обоснование: `questionnaire_subjects` создаёт второй источник истины для предмета анкеты. При наличии `questionnaires.subject_id` отдельная M2M-связь для анкет не нужна и может привести к рассинхронизации.

### 10.9. Удаление модуля `purchases`

В текущей схеме присутствует модуль `purchases`:

- таблица `purchases`;
- таблица `promo_codes`;
- модели `Purchase` и `PromoCode`;
- связи с `student_profiles` и `tutor_profiles`.

В актуальных сценариях и ближайших планах этого функционала нет.

Решение:

- удалить таблицу `purchases`;
- удалить таблицу `promo_codes`;
- удалить модели `Purchase` и `PromoCode`;
- убрать связи `StudentProfile.purchases` и связанные импорты;
- убрать связи/импорты из `TutorProfile`, если они есть;
- убрать модуль `app/modules/purchases`, если в нём не останется другой актуальной логики.

Обоснование: финансовая модель и промокоды пока не описаны сценариями. Хранить заранее спроектированные таблицы без продуктового основания не нужно: это усложняет схему, миграции и дальнейшее сопровождение.

### 10.10. Участники диалога в `conversations`

В текущей схеме `conversations` хранит участников двумя способами одновременно:

- `student_id` → `student_profiles.id`;
- `tutor_id` → `tutor_profiles.id`;
- `student_user_id` → `users.id`;
- `tutor_user_id` → `users.id`.

Такой вариант признан избыточным. Диалог является отношением между двумя пользователями в конкретных ролях, поэтому достаточно хранить ссылки на `users`. Профили ученика и преподавателя при необходимости получаются через связь от пользователя к профильной таблице.

Решение:

- удалить `conversations.student_id`;
- удалить `conversations.tutor_id`;
- оставить `conversations.student_user_id` как FK → `users.id`, NOT NULL;
- оставить `conversations.tutor_user_id` как FK → `users.id`, NOT NULL;
- оставить `conversations.initiator_id` как FK → `users.id`, NOT NULL;
- сохранить уникальное ограничение на пару `(student_user_id, tutor_user_id)`;
- удалить relationship со стороны `Conversation` на `StudentProfile` / `TutorProfile`;
- удалить обратные relationship `conversations_as_student` / `conversations_as_tutor` из профильных моделей, если они больше не нужны.

Дополнительные правила:

- `student_user_id` должен указывать на пользователя с ролью ученика;
- `tutor_user_id` должен указывать на пользователя с ролью преподавателя;
- `initiator_id` должен быть равен либо `student_user_id`, либо `tutor_user_id`;
- сервер должен проверять роли участников при создании диалога.

Обоснование: хранение одновременно profile-id и user-id создаёт два источника истины и риск рассинхронизации. Для уникального ограничения «один диалог на пару ученик-репетитор» достаточно пары `student_user_id` + `tutor_user_id`.

### 10.11. Правки документов верификации и внешних отзывов

#### `external_review_requests.declared_count`

В текущей схеме `external_review_requests` содержит поле `declared_count` — заявленное преподавателем количество отзывов на внешней платформе.

Решение:

- убрать поле `external_review_requests.declared_count`.

Обоснование: заявленное количество отзывов не является надёжным источником истины. Фактическое количество должен определять модератор или парсер при обработке ссылки. Если в будущем потребуется хранить результат проверки, лучше фиксировать фактически импортированное количество через связанные записи `external_reviews` или отдельные поля результата обработки, а не через пользовательский ввод.

#### Файлы документов верификации

В текущей схеме `verification_documents` содержит поле `file_keys` как `JSONB`.

Такой вариант неудобен для управления жизненным циклом файлов: документы должны храниться ограниченное время, файлы нужно удалять, а по каждому файлу может понадобиться отдельная техническая информация.

Решение:

- убрать `verification_documents.file_keys`;
- создать отдельную таблицу `verification_document_files`;
- хранить каждый файл документа отдельной строкой;
- срок хранения и удаление файлов контролировать на уровне отдельных файлов.

Предлагаемая новая таблица:

### `verification_document_files`

Файлы, прикреплённые к документу верификации.

| Поле        | Тип                                              | Комментарий                        |
| ----------- | ------------------------------------------------ | ---------------------------------- |
| id          | UUID, PK                                         |                                    |
| document_id | UUID, FK → `verification_documents.id`, NOT NULL | Документ верификации               |
| storage_key | String, NOT NULL                                 | Ключ файла в объектном хранилище   |
| file_name   | String, NULL                                     | Исходное имя файла                 |
| mime_type   | String, NULL                                     | MIME-тип                           |
| size_bytes  | Integer, NULL                                    | Размер файла                       |
| created_at  | datetime, NOT NULL                               | Время загрузки                     |
| expires_at  | datetime, NULL                                   | Когда файл должен быть удалён      |
| deleted_at  | datetime, NULL                                   | Когда файл был удалён из хранилища |

Обоснование: отдельная таблица лучше подходит для удаления файлов по истечении срока хранения, повторных попыток удаления, аудита и будущего расширения. `JSONB file_keys` годится для простого хранения массива ключей, но плохо выражает состояние каждого файла.
