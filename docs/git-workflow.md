# Git Workflow

> Мануал по работе с Git для команды. Определяет правила веток, коммитов, PR и ревью.
>
> **Важно:** из-за ограничений бесплатного плана GitHub branch protection rules недоступны. Все правила ниже — **процедурные**, их обязуется соблюдать каждый член команды.

## 1. Структура веток

```
main (продакшен — стабильная версия, только релизы)
  └── develop (основная разработка — повседневная интеграция)
       ├── feature/XXX-описание
       └── fix/XXX-описание
```

### Описание веток

| Ветка       | Назначение                                                 | Правило мёржа                                  |
| ----------- | ---------------------------------------------------------- | ---------------------------------------------- |
| `main`      | Продакшен. Всегда стабильный, деплоабельный код.           | Только из `develop`. Прямые коммиты запрещены. |
| `develop`   | Основная ветка разработки. Сюда мержатся все фичи и фиксы. | Только из `feature/*` или `fix/*` через PR.    |
| `feature/*` | Новая функциональность. Удаляется после мёржа.             | Ветвится от `develop`, PR в `develop`.         |
| `fix/*`     | Исправление багов. Удаляется после мёржа.                  | Ветвится от `develop`, PR в `develop`.         |
| `hotfix/*`  | Срочный багфикс продакшена (см. раздел 5).                 | Ветвится от `main`, PR в `main`.               |

### Когда какие ветки использовать

- **Новая фича** → `feature/GH-123-описание`
- **Багфикс** → `fix/GH-124-описание`
- **Срочный фикс продакшена** → `hotfix/GH-125-описание` (см. раздел 5)

## 2. Жизненный цикл PR

```
┌─────────────────────────────────────────────────────────────────┐
│                        Flow PR                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. Создать ветку                                               │
│     git checkout -b feature/XXX develop                         │
│                          │                                      │
│  2. Писать код + коммиты                                        │
│                          │                                      │
│  3. Запушить                                                    │
│     git push -u origin feature/XXX                              │
│                          │                                      │
│  4. Открыть PR                                                  │
│     GitHub: New Pull Request → base: develop                    │
│                          │                                      │
│  5. CI запускается автоматически                                │
│     (линтеры, unit-тесты, билд)                                 │
│                          │                                      │
│  ├── CI зелёный → ревью                                         │
│  └── CI красный → фиксить (см. раздел 8)                        │
│                          │                                      │
│  6. Ревью + аппрувы                                             │
│     (минимум 1 approver, автор не мержит себя)                  │
│                          │                                      │
│  7. Мёрдж в develop                                            │
│     (Squash and merge или Rebase and merge)                     │
│                          │                                      │
│  8. Удалить feature-ветку                                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Релизный цикл (develop → main)

```
develop (фичи накопились, протестированы)
    │
    ▼
PR в main → релиз
```

## 3. Процесс работы над фичей

### Шаг 1: Создание ветки

```bash
# Обновить develop
git checkout develop
git pull origin develop

# Создать feature-ветку от develop
git checkout -b feature/GH-123-login-form develop
# Или (Git 2.23+): git switch -c feature/GH-123-login-form develop
```

### Шаг 2: Работа и коммиты

```bash
# Работаем, сохраняем изменения
git add .
git commit -m "feat(auth): добавить базовую форму логина"

# Пушим в remote
git push -u origin feature/GH-123-login-form
```

### Шаг 3: Открытие PR

1. Открываешь GitHub → вкладка **Pull requests** → **New pull request**
2. **base:** `develop`
3. **compare:** `feature/GH-123-login-form`
4. Заполняешь шаблон PR (см. ниже)
5. Нажимаешь **Create pull request**

### Шаблон PR

```markdown
## Что делает

Кратко. Можно списком

## Связанные задачи

- #{Номер-Issue}

## Чеклист

- [ ] Тесты прошли
```

**#{Номер-Issue}** - _Тут нужно указать номер связанного Issue. После мёржа PR — закрыть Issue руками._

### Шаг 4: После мёржа

```bash
# Переключиться обратно на develop
git checkout develop
# Или (Git 2.23+): git switch develop
git pull origin develop

# Удалить старую ветку (локально и remote)
git branch -d feature/GH-123-login-form
git push origin --delete feature/GH-123-login-form
```

## 4. Ревью кода

### Кто ревьюит

Ревью вашего PR вы можете попросить у кого угодно. Смотрите по загруженности, или может есть люди, кто лучше погружен в контекст вашей задачи

### Правила ревью

1. **Автор не мержит свой PR** — это золотое правило, без исключений.
2. **Минимум 1 approver** перед мёрджем.
3. **Срок ответа на ревью:** По хорошему лучше находить время для Review, иначе разработка будет стопориться. Если задерживаешься — предупреди автора.
4. **После правок:** автор пушит фиксы, ревьюер перепроверяет и ставит approve.
5. **Если один человек не может провести Review**: попроси другого

### Как оставлять комментарии

Когда ревьюите код, то напишите буквально пару слов о том, что вы думаете.

- Если все гуд по вашему мнению, то так и напишите, после этого ставьте апрув.
- Если есть замечания, опишите их

### Процесс аппрува

```
PR открыт
    │
    ▼
Ревьюер смотрит код
    │
    ├── Есть замечания → Request changes → автор правит → снова на ревью
    │                                                          │
    └── Всё ок → Approve → (ждём остальные аппрувы если нужно)
                                                              │
                                              Минимум 1 approve получен
                                                              │
                                                              ▼
                                                     Автор может мержить
                                                     (но не себя!)
```

## 5. Hotfix и Rollback

### Когда нужен hotfix

Баг обнаружен на проде (в `main`) и не может ждать следующего релиза через `develop`.

### Процесс hotfix

```
main (баг на проде)
    │
    └── hotfix/critical-bug (от main)
          │
          ├── 1. CI прогон (тесты + линтеры)
          ├── 2. PR в main → мёрж
          ├── 3. PR из hotfix в develop (бэкпорт)
          └── 4. Удалить hotfix-ветку
```

**Шаги:**

1. Создать ветку от `main`: `hotfix/GH-456-краткое-описание`
2. Исправить баг, закоммитить
3. Дождаться зелёного CI
4. Открыть PR в `main` — аппрув обязателен
5. После мёржа в `main` — **обязательно** создать PR из той же `hotfix/` ветки в `develop` (бэкпорт), чтобы фикс не потерялся при следующем релизе
6. Удалить hotfix-ветку

### Аппрув для hotfix

- Минимум 1 approver (как и для обычного PR)
- Ревью ускоренное: автор пишет в чат "hotfix, нужен быстрый аппрув"
- Если ревьюера нет в данный момент — автор может самомержить, но с обязательным ревью после факта и фиксацией в задаче

### Когда делать откат (Rollback) вместо hotfix

- Если баг критический (падение сервиса, утечка данных) и времени на правку нет
- Если фикс сложнее, чем кажется на первый взгляд
- Если ответственный за модуль недоступен

**Откат через git revert:**

```bash
git checkout main
git revert HEAD --no-commit
git commit -m "fix: откат предыдущего коммита, сломал прод"
git push origin main
```

После отката — создать задачу на фикс и пройти обычный процесс через `develop`.

## 6. Conventional Commits

Используем стандарт Conventional Commits с описаниями на русском языке.

### Формат

```
<type>(<scope>): <description>

<body (опционально)>
```

### Типы

| Тип        | Когда использовать                    | Пример                                         |
| ---------- | ------------------------------------- | ---------------------------------------------- |
| `feat`     | Новая функциональность                | `feat(auth): добавить OAuth2 через Google`     |
| `fix`      | Исправление бага                      | `fix(api): исправить 500 при пустом email`     |
| `docs`     | Изменения документации                | `docs(readme): добавить инструкцию по запуску` |
| `style`    | Форматирование, точки с запятой, etc. | `style: привести отступы к стандарту`          |
| `refactor` | Рефакторинг без изменения поведения   | `refactor(db): вынести запросы в Repository`   |
| `test`     | Добавление/исправление тестов         | `test(users): покрыть метод createUser`        |
| `chore`    | Зависимости, конфигурация             | `chore: обновить pytest до версии 8.0`         |

### Scope (область)

Scope — короткое обозначение модуля или компонента:

**Backend (FastAPI):**

- `auth` — аутентификация, авторизация
- `api` — эндпоинты, роутеры
- `db` — модели, миграции, репозитории
- `services` — бизнес-логика
- `utils` — хелперы, утилиты

**Frontend (Next.js):**

- `ui` — компоненты
- `pages` — страницы
- `hooks` — кастомные хуки
- `store` — состояние (context, zustand, etc.)
- `api` — API клиент

### Примеры хороших коммитов

```bash
# Хорошие
feat(auth): добавить форму регистрации с валидацией
fix(api): обработать 404 при отсутствии пользователя
test(db): покрыть UserRepository интеграционными тестами
refactor(auth): вынести JWT логику в отдельный сервис

# Плохие ❌
fix(починил баг)
делал фичу
update
wip
feat: правки
```

### Формат названия PR

```
<type>(<scope>): <description> (#<ticket>)
```

Примеры:

- `feat(auth): форма регистрации (#GH-123)`
- `fix(api): обработка отсутствующего пользователя (#GH-45)`
- `test(db): покрыть UserRepository тестами (#GH-67)`

## 7. CI-пайплайн

CI запускается автоматически при:

- Push в `develop`
- Pull request в `develop`
- Push в `main` (для hotfix и smoke-тестов)

### Что бегает на develop

```
┌─────────────────────────────────────────────┐
│           CI Pipeline (develop)              │
├─────────────────────────────────────────────┤
│                                             │
│  1. Линтинг                                 │
│     ├── Backend: ruff + mypy               │
│     └── Frontend: eslint + prettier         │
│                    │                        │
│                    ▼                        │
│  2. Unit-тесты                             │
│     ├── Backend: pytest                    │
│     └── Frontend: vitest / jest            │
│                    │                        │
│                    ▼                        │
│  3. Билд-чек                               │
│     ├── Backend: проверка сборки           │
│     └── Frontend: next build               │
│                                             │
└─────────────────────────────────────────────┘
```

### Что бегает на main

```
┌─────────────────────────────────────────────┐
│            CI Pipeline (main)               │
├─────────────────────────────────────────────┤
│                                             │
│  1. Smoke-тесты (быстрая проверка)          │
│     ├── Backend: GET /ping                  │
│     └── Frontend: страница грузится         │
│                                             │
└─────────────────────────────────────────────┘
```

## 8. Что делать если тесты упали

### Алгоритм действий

```
Тесты упали на CI
       │
       ▼
1. Открыть логи CI в GitHub Actions
       │
       ▼
2. Определить что именно упало:
   ├── Линтинг → исправить стиль/форматирование
   ├── Unit-тесты → баг в коде или тест устарел
   └── Билд → ошибка компиляции/сборки
       │
       ▼
3. Воспроизвести локально:
   Backend: pytest -v
   Frontend: npm test
       │
       ▼
4. Исправить
       │
       ▼
5. Закоммитить и запушить fix
   git commit -m "fix(tests: исправить падающий тест"
   git push
       │
       ▼
6. CI перезапустится автоматически
       │
       ▼
7. Дождаться зелёного статуса → можно мержить
```

### Важные правила

- **Не мержить PR с красным CI** — никогда, ни при каких условиях.
- **Если тест устарел** (код поменялся, тест больше не валиден) — обновить тест в том же или отдельном коммите.
- **Если флапающий тест** (падает нестабильно) — создать задачу на починку.

## 9. Правила и запреты

### ✅ Делать так

- Ветвиться от `develop` для новых фич
- Писать коммиты по стандарту Conventional Commits
- Открывать PR в `develop` (не в `main`)
- Ждать минимум 1 approver перед мёржем
- Мержить только при зелёном CI
- Удалять feature-ветки после мёржа (кнопка **Delete branch** в PR после мёржа)
- Пуллить `develop` перед новой веткой
- Писать понятные описания PR

### ❌ Не делать так

- Коммитить прямо в `main` или `develop`
- Мержить свой собственный PR
- Мержить с красным CI ("и так сработает")
- Писать коммиты типа `fix`, `update`, `wip`
- Пушить чувствительные данные (tokens, passwords)
- Держать долгоживущие feature-ветки (более 2 недель)
- Force push в общие ветки (`develop`, `main`)

### ⚠️ Нарушения правил

При обнаружении нарушения:

1. **Первый раз** — устное напоминание в команде
2. **Второй раз** — обсуждение на дейли/групповом чате
3. **Систематическое** — выносится на ретроспективу, возможны изменения процесса

## Быстрая шпаргалка

```bash
# Начать работу над фичей
git checkout develop && git pull
git checkout -b feature/GH-123-краткое-описание develop
# Или (Git 2.23+): git switch -c feature/GH-123-краткое-описание develop

# Коммитить
git add . && git commit -m "type(scope): описание"

# Запушить и создать PR
git push -u origin feature/GH-123-краткое-описание
# → Открыть GitHub → Create PR → base: develop

# После мёржа
git checkout develop && git pull
git branch -d feature/GH-123-краткое-описание
git push origin --delete feature/GH-123-краткое-описание

# Синхронизация с develop (если кто-то успел смержить)
git checkout feature/GH-123-краткое-описание
git rebase develop

# Hotfix (срочный багфикс продакшена)
git checkout main && git pull
git checkout -b hotfix/GH-456-критический-баг main
# ... фикс + коммит ...
git push -u origin hotfix/GH-456-критический-баг
# → PR в main → аппрув → мёрж
# → PR из той же hotfix/ в develop (бэкпорт)

# Rollback (откат через git revert)
git checkout main
git revert HEAD --no-commit
git commit -m "fix: откат предыдущего коммита"
git push origin main
<<<<<<< HEAD
# После отката — создать задачу на фикс и пройти через develop
=======
>>>>>>> origin/develop
```
